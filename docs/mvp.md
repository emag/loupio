# Lupio MVP — 合意済みの範囲

## 目的

多数の GitHub PR から今自分が対応すべきものを見つけ、明確な観点に沿ってレビューする。利用者はまず本人一人。対象 OS は macOS と Linux。一日に確認する PR は約10件、一覧に残る PR は約30件。

現在利用している GitHub クライアントでは長時間起動した際のフリーズと、対応すべき PR を探す手間が課題。フリーズの原因は未調査。

## 作業の流れ

1. 個人宛て・所属チーム宛てのレビュー依頼を自動収集する。URL で手動追加もできる。
2. 要対応の PR を選び、GitHub や IDE でコードを確認・コメント・承認する。
3. PR ごとに確認観点の状態、短いメモ、仕様の根拠リンクを保存する。
4. 対応状況を更新し、追加コミットや返信があれば再確認する。
5. 再起動しても記録した内容から再開する。

## 対応状況

- 要対応：レビュー依頼や、レビュー後の追加コミット・返信により、自分の対応が必要。
- 相手待ち：自分の指摘や質問に対する作者の対応を待っている。
- 対応済み：自分のレビューを完了し、新たな対応が発生していない。
- 終了：PR がマージまたはクローズされた。

既読・未読とは分ける。追加コミットや返信により要対応に戻し、理由を表示する。相手待ち・対応済みは手動設定でき、自動判定も手動修正できる。

チーム依頼は要対応に表示する。「自分は対応しない」を選べる。他メンバーの承認だけでは自動的に一覧から外さない。対象外にした PR は追加コミットや通常の返信では再表示せず、個人宛てのレビュー依頼で要対応に戻す。手動でも一覧に戻せる。

追加コミット時は以前の確認記録を保持し、四つの観点を再確認が必要として表示する。返信のみの場合は観点の確認結果を維持し、PR を要対応に戻す。

コメントによる再表示は、作者の新しいコメント・返信と、自分へのメンションを対象にする。自分自身と Bot のコメントは除外する。個人宛ての再レビュー依頼でも要対応に戻す。

一度取り込んだ PR はレビュー依頼が解除されても、マージ・クローズまで追跡する。「自分は対応しない」にした PR には前述の除外ルールを適用する。

ドラフト PR は通常の要対応一覧から外し、別途表示できる。ドラフト解除時に要対応として表示する。ドラフト中でも手動で要対応にできる。

## 接続先

初版は GitHub.com の単一アカウントに対応する。所属チームからレビュー依頼の収集対象を選択できる。

認証はブラウザで GitHub にログインして接続を許可する方式を第一候補とする。認証情報は OS の資格情報保管機能に保存する。具体的な方式は所属組織の制約と実装上の対応可否を確認して確定する。

初回は現在レビュー依頼が残っている未終了 PR を要対応として取り込む。それ以外は URL で手動追加する。

## 保存と更新

メモ・確認記録・優先指定などは端末内に保存する。初版では macOS と Linux の端末間同期は行わない。GitHub 上の情報は各端末で取得する。

起動時・起動中の約1分ごと・手動操作で更新し、最終更新時刻と取得失敗を表示する。通信できない間も保存済みの一覧やメモを閲覧・編集できる。

メモ・確認記録・設定を手動でファイルに書き出し、復元できる。認証情報は書き出さない。

手動で優先指定した PR を先頭にし、それ以外は対応待ちが長い順にする。直接依頼・チーム依頼の区別と再確認の理由を表示する。

## レビューポリシー

初期の確認観点は以下の四つ。各観点に未確認・確認済み・対象外と短いメモを残せる。

- 仕様との一致
- 既存の仕様・振る舞いとの整合
- ユニットテストの十分性
- セキュリティ

根拠となる仕様書・Jira・Slack などのリンクを手動で紐づける。リンク先の自動取得は必要性を見て判断する。

## 外部ツールと将来の範囲

既存の Claude などのレビュー結果を参照する。結果のある場所へのリンクや、必要な抜粋をメモとして保存する。Lupio が AI レビューを実行する機能は後で判断する。

将来はコード以外のレビュー対象ドキュメントも統合管理したい。

## 完成条件

上記の流れが macOS・Linux で実行でき、約30件を一覧管理しながら一日約10件の確認作業に使える。

普段使う macOS・Linux の端末で、以下を確認する。

- 一覧約30件の保存済みデータを、起動から3秒以内に操作できる。
- 一覧の切り替えやメモの入力は通信完了を待たずに操作できる。
- 約8時間起動して定期取得を続けてもフリーズせず、操作感が悪化しない。

測定端末・具体的な操作と計測方法は検証計画で定める。

## まだ決めていないこと

認証方式の実現性と組織の制約、GitHub API による収集・更新検知の実現方法、データ保存・復旧の詳細、技術構成、性能検証の測定条件。これらは技術調査・設計で詰め、利用者の判断が必要な制約や仕様変更が判明した場合は確認する。
