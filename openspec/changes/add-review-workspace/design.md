# Design

## Context

合意範囲は docs/mvp.md、根拠と候補比較は docs/technical-research.md を参照する。アプリ実装はまだない。本設計の技術構成は試作前の第一候補であり、認証方式を含め実測が必要。

## Goals / Non-Goals

個人の対応待ち PR とレビュー記録を端末内で管理する。コード閲覧・GitHub へのコメント投稿・承認は外部で行う。初版では端末間同期、AI の実行、仕様リンク先の自動収集、GitHub Enterprise Server、汎用ドキュメントレビューは対象外。

## Decisions

- 第一候補は Tauri 2、TypeScript UI、Rust のドメイン・API・保存処理、SQLite。WebView の UI はローカル資産だけを表示し、外部リンクは OS のブラウザに渡す。
- レビューポリシーは四観点の固定初期値とする。追加コミット時は確認の履歴を残し、再確認フラグを立てる。返信のみでフラグを立てない。
- ローカルの追跡対象集合を検索結果と分ける。GitHub の依頼から消えても追跡を続ける。
- PR の観測状態と利用者の操作を分離する。安定 ID、head SHA、イベント ID、取得境界、利用者が確認した境界を保持する。
- 更新は起動・約一分のタイマー・手動・スリープ復帰を一つのキューにまとめる。重複実行せず、API の制限時はバックオフし遅延を表示する。
- DB の更新はトランザクション化する。同期は利用者のメモ・対象外指定を消さない。アカウント ID を記録に結びつける。
- バックアップは版付きのデータ形式とし、検証後に全体置換する復元を候補とする。置換前の内容は保持し失敗時はロールバックする。認証情報は含めない。

## State transitions

| 条件 | 処理 |
| --- | --- |
| マージ・クローズ | 終了を優先 |
| 対象外への個人宛て新規依頼 | 対象外を解除し要対応へ |
| 対象外への通常更新 | 対象外を維持 |
| ドラフト（手動要対応指定なし） | 通常一覧から外す |
| ドラフト解除 | 要対応へ |
| 新しい head SHA | 過去の観点結果を残して再確認を表示、要対応へ |
| 作者コメント・自分へのメンション・再依頼 | 自分と Bot を除外し、要対応へ |
| 同一イベントの再取得 | 状態を変えない |
| 利用者の手動変更 | その時点までの確認境界と一緒に保存 |

対象外やドラフトで非表示の場合にも追加コミットによる観点の再確認必要性は保存する。通常の要対応一覧への表示は対象外・ドラフトの規則を優先する。PR の再オープン、コメント編集、チーム脱退等の境界例は実装前の状態遷移テストで扱い、既存合意から判断できない点は仕様に追記して確認する。

## Risks / Trade-offs

Tauri の Linux 依存と OS 間差分は実機確認が必要。30件の全 API を毎分取得する方式は予算超過の可能性がある。条件付き取得でも通信回数と二次制限に注意する。検索やポーリングだけでは一時イベントの完全検知を保証しない。

ブラウザ OAuth の secret を配布物に埋め込まない。交換サービスの追加か device flow 等の選択が必要で、GitHub App の権限設計も比較する。サービス運用はまだ承認された構成ではないため、登録・公開・配布は行わない。

## Validation

状態遷移、重複・部分取得、ページング、レート制限、オフライン編集との競合、バックアップ復元を重点的に検証する。macOS・Linux の端末と OS バージョンを記録し、30件でコールドスタートを各5回測定する。3秒目標の起点はプロセス起動、終点は一覧の選択・入力が可能になった時点。8時間試験では約1分の取得と10件相当の確認操作を行い、フリーズ、入力遅延、メモリ推移、API 数を記録する。操作感悪化の数値基準は基準端末の試作測定後に固定する。

## Open Questions

認証方式と組織承認、対象 Linux ディストリビューション、資格情報ストア、性能測定端末、配布・署名方法は試作で確認する。現時点で実装や性能検証が完了したとは扱わない。
